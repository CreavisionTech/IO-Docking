# I2C 工作台设计(index.html 内建,免固件改动)

> **状态:已实现** —— `web/index.html` 的 I2C 标签页已改造完成,内置 MPU6050 定义,离线验证全部通过。

## 1. 一句话设计

**页面只做「读 → 解码 → 展示 → 写」,设备知识不写进网页,而是由 AI 生成一份「设备定义」粘贴进来。**
定义只负责**列出该器件所有可读/可写的量**,真正读哪些、写什么,由用户在页面上决定。

这样 `demo/demo_mpu6050_iic.html` 这类单设备专用页面就不再必要 —— 换器件 = 换一份定义,而不是再写一个 HTML。

三条主线:

| 能力 | 做法 |
| --- | --- |
| **开箱即用** | 用户拿到定义只需三步:解析并启用 → 初始化设备 → 开始轮询。**没有任何手工配置**,数值表和曲线直接出来 |
| **读什么,定义说清** | `fields` 目录声明每个量的地址/位段/换算;`poll:false` 标记不必每帧读的配置与状态。页面**自动把地址相邻的字段合并成尽量少的 I2C READ** |
| **写什么,定义说清** | `write:true` + `type:'bits'` 声明位段 → 页面走**读-改-写**,不破坏同寄存器其它 bit;`commands` 声明一键动作命令 |
| **器件寄存器太多** | `group` 分组 + `desc` 说明;数值表分组显示,写入面板也按分组 |

---

## 2. 为什么是这个形状(与被放弃的重设计对比)

初版设计围绕「设备档案」搭了一套完整引擎:寄存器清单表格(逐行填类型/字节序/换算/位域)、
枚举编辑器、位域编辑器、模板选择器、量程联动…… 这些被砍掉的理由:
**它们都是在"替用户拼配置"**,而配置本来就该由 AI 从数据手册生成。

中途我试过让用户在页面上逐个**勾选**要读的量 —— **这个方案已经去掉**。理由是它把配置负担推给了用户:
每换一个器件都要先研究一遍它的寄存器、再决定勾哪些,这与「AI 辅助下快速读取并展示」的目标相反。
现在把这部分判断也交给 AI:定义里用 `poll` / `plot` / `group` 三个标记表达
「每帧读哪些、哪些画曲线、怎么分组」,用户只需要点按钮。

| 环节 | 谁负责 |
| --- | --- |
| 读哪些量、哪些画曲线、怎么分组 | **AI**(在定义里用 poll/plot/group 表达) |
| 地址、位段、换算系数、初始化序列 | **AI**(照数据手册写定义) |
| 只在要改参数时填空、点按钮 | **用户** |
| 合并读取、解码换算、反向换算、读-改-写、画图、导出 | **页面** |

设计要点:

- **单一「目标地址」**:读 / 写 / 轮询 / 初始化 / 命令 共用。原有的 `i2cAddr` 与 `i2cWAddr`
  两份输入已合并(手动写卡也改用同一地址框)。
- **`def.addr` 只是初值**,解析定义时填进地址框;**之后地址框才是唯一真相**,改地址不必改定义。
- **8 位地址自动折算**:输入 `D0` 会按 7 位 `0x68` 处理并提示。
- **数值表按 `group` 分组显示**,分组标题占一整行 —— 寄存器多的器件才看得过来。
- **「📖 读全部量」**读一次定义里的所有量(含 `poll:false` 的配置/状态),按分组列出当前值,用于核对配置。
- 手动读写**默认折叠**,把版面让给工作流,但完整保留 —— 原有 6 个函数签名未变。

## 4. 设备定义格式(核心参考)

`web/index.html` 里的 `I2C_DEF_DEFAULT` 就是内置的 MPU6050 定义,可直接当模板改。

```js
{
  name: 'MPU6050', addr: 0x68,
  init: [ [0x6B,0x00], [0x1A,0x03],     // 可选:一键初始化序列
          [0x1C,0x00], [0x1B,0x00] ],

  fields: [
    // 实时数据:每帧读、并画曲线
    { group:'实时数据', key:'ax', label:'加速度 X', unit:'g',
      reg:0x3B, len:2, type:'s16', div:16384, plot:true },
    { group:'实时数据', key:'temp', label:'温度', unit:'°C',
      reg:0x41, len:2, type:'s16', div:340, bias:36.53, plot:true },

    // 状态:默认不勾,想查时勾上
    { group:'状态', key:'who', label:'WHO_AM_I', desc:'固定 0x68(兼容件 0x70)',
      reg:0x75, len:1, type:'u8' },

    // 配置:可写。位段用 bits 声明,页面自动读-改-写
    { group:'配置', key:'arange', label:'加速度量程', desc:'ACCEL_CONFIG bit3-4 AFS_SEL',
      reg:0x1C, len:1, type:'bits', bit:3, bits:2,
      enum:{0:'±2g',1:'±4g',2:'±8g',3:'±16g'}, write:true },
    { group:'配置', key:'srate', label:'采样分频', desc:'采样率 = 1kHz/(1+该值)',
      reg:0x19, len:1, type:'u8', write:true },
  ],

  commands: [
    { key:'wake',  label:'唤醒',           reg:0x6B, data:[0x00] },
    { key:'reset', label:'复位所有寄存器',  reg:0x6B, data:[0x80], confirm:true },
  ],
}
```

### 4.1 顶层字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 否 | 显示名;同时用作 CSV 文件名 |
| `addr` | 否 | 7 位地址;解析时填入地址框,之后以地址框为准 |
| `init` | 否 | 初始化写序列,点「⚡ 初始化设备」才执行 |
| `fields` | **是** | 可读量目录(见 4.2) |
| `commands` | 否 | 一键动作命令(见 4.4) |

> 旧的 `read` + `decode` 格式仍兼容(每次读整块),但**不再推荐**:
> 它无法让用户挑选读哪些量,也无法声明写入。新定义请用 `fields`。

### 4.2 `fields` 每一项 —— 读的部分

| 字段 | 说明 |
| --- | --- |
| `key` | 唯一标识(英文/数字/下划线),不要重复 |
| `label` | 中文显示名(必填,用户就靠它认) |
| `group` | 分组名。**寄存器多时这是能不能看过来关键**;数值表与写入面板都按它分组 |
| `poll` | 设 `false` = 不进轮询,只在「📖 读全部量」时读一次。状态/配置/ID/校准都该设,否则每帧多出 I2C 往返 |
| `desc` | 一句话说明。位段含义写这里,如 `'ACCEL_CONFIG bit3-4 AFS_SEL'` |
| `unit` | 物理单位;字符串型的量可省 |
| `reg` | 该量所在寄存器 |
| `len` | 字节数;省略时由 `type` 推出 |
| `type` | `u8 s8 u16 s16 u24 s24 u32 s32 float32 bits ascii` |
| `endian` | 省略默认大端;小端写 `'le'` |
| `bit` / `bits` | `type:'bits'` 时必填:起始位 / 位宽 |
| `mul` / `div` / `bias` | 线性换算 `值 = 原始 × mul ÷ div + bias`(默认 1/1/0) |
| `enum` | 值→文字映射,如 `{0:'±2g',1:'±4g'}` |
| `plot` | 默认是否画曲线(用户仍可改)。实时数据设 `true` |

**`len` 推导规则**:`u8/s8=1`、`u16/s16=2`、`u24/s24=3`、`u32/s32/float32=4`、`bits=1`。

**为什么用 `div` 而不是比例系数**:照数据手册抄的时候,填 `div:16384` 比填 `0.0000610352`
直观得多,也不容易抄错。温度那种带偏移的用 `div:340, bias:36.53`。

### 4.3 `fields` 每一项 —— 写的部分

不写 `write` 就不可写。可写时有**两条硬规则**:

| 情况 | 声明方式 | 页面行为 |
| --- | --- | --- |
| 该量**只占寄存器的一部分**(有位段) | **必须** `type:'bits'` + `bit`/`bits` | 先读该寄存器 → 清掩码、填新值 → 写回。**不会破坏同寄存器其它 bit** |
| 该量**占满整个寄存器** | 整数类型(`u8`/`s16`/…) | 直接写整个寄存器 |

两种都配合 `mul/div/bias` 与 `enum`,页面会自动做**反向换算** ——
例如量程下拉选「±8g」,页面自己算出位值 2 再写进去;输入 `4` 到 `div:16384` 的字段,
页面写出 `0x40 0x00`。**写入后自动读回校验**,并把实际值写进日志。

数值超出类型范围时会**夹紧**并告警(例如往 `u8` 写 999 → 255)。

`float32` 与 `calc` 字段**不可写**(明确报错,不静默失败)。

### 4.4 `commands` —— 一键动作命令

用于「写一个固定字节序列做一件事」:复位、开始转换、校准、软复位……

```js
commands: [
  { key:'wake',  label:'唤醒',           reg:0x6B, data:[0x00] },
  { key:'reset', label:'复位所有寄存器',  reg:0x6B, data:[0x80], confirm:true },
]
```

- `data` 是要写的字节数组(**不要写成字符串**)。
- `confirm:true` 表示有破坏性,页面会弹确认框并在按钮上标 ⚠。
  软复位 / 校准 / 清空数据之类**都必须设 `true`**。

### 4.5 非线性器件:`deps` + `calc`

换算涉及补偿算法、跨字节打包、或依赖校准寄存器时,单个 field 写成:

```js
{ group:'实时数据', key:'temp', label:'温度', unit:'°C',
  deps: { cal:{reg:0x88,len:24}, data:{reg:0xF7,len:6} },
  calc: x => (在这里写补偿计算,用 x.cal / x.data 取字节) }
```

`deps` 声明这个量需要读哪几段寄存器;`calc` 收到按 `deps` 的键索引的对象,
值是 `Uint8Array`。**带 `calc` 的量不可写。**

### 4.6 `calc` 里可用的助手

多字节默认**大端**,末参传 `'le'` 改小端:

| 助手 | 说明 |
| --- | --- |
| `u8(b,o)` `s8(b,o)` | 单字节无/有符号 |
| `u16(b,o,e)` `s16(b,o,e)` | 双字节 |
| `u24(b,o,e)` `s24(b,o,e)` | 三字节 |
| `u32(b,o,e)` `s32(b,o,e)` | 四字节 |
| `float32(b,o,e)` | IEEE754 单精度 |
| `bits(b,o,起始位,位数)` | 取寄存器内连续若干 bit |
| `ascii(b,o,len)` | 定长字符串,不可打印字符显示为 `.` |

`o` 是字节偏移(0 = 该 `Uint8Array` 的第 1 个字节)。普通 JS 运算、`Math.*`、局部变量也都能用。

## 5. 关键实现要点

### 5.1 合并读取:定义里的 poll 决定 I2C 往返次数

页面把**参与轮询的字段**(`poll !== false`)占用的寄存器区间收集起来,按地址排序后
**贪心合并相邻/重叠区间**,每个区间一条 `I2C READ`。所以 `poll` 不只是显示问题,
它直接决定帧率 —— 这也是把 `poll` 判断交给 AI 的原因。

| 定义里的 poll | 合并结果 | 每次采样的 I2C 往返 |
| --- | --- | --- |
| 只把 7 个实时数据设为轮询(0x3B..0x48) | `0x3B+14` | **1 次** |
| 把 WHO_AM_I(0x75)也设为轮询 | `0x3B+14` + `0x75+1` | 2 次 |
| 再把加速度量程(0x1C)也设为轮询 | `0x1C+1` + `0x3B+14` + `0x75+1` | 3 次 |

界面上直接显示这个计划(「每次采样读 N 个量 → 合并为 M 次 I2C READ(...)」),
并说明另有几个量标了 `poll:false` —— 用户一眼能看出定义有没有写对。

**上限**:响应行受 512B 行缓冲限制(`Doc/Host_Protocol.md` 442 行),
单条读取封顶 **200 字节**,超长区间自动拆分。

### 5.2 轮询必须用链式串行,不能用 `setInterval`

`demo/demo_mpu6050_iic.html` 用的是 `setInterval` + 标志位,搬到通用页有两个问题:

1. **请求堆积** —— `sendCommand` 是单请求队列,前一条没回来时新请求只会排队,采样周期被拉长且抖动。
2. **迟到响应串帧**(更严重) —— `acceptResponse` 按**命令关键字**匹配响应,而文本协议
   **没有事务编号**(见 `index.html` 中 `sendCommand` 上方注释)。轮询每帧发的字符串完全相同,
   一旦某帧响应迟到,它会匹配到**下一帧**的请求上,造成**静默的一帧错位** —— 数据看着正常但整体偏移。

实现要点:每帧**严格串行** `await`,下一帧在上一帧结束后才排期;周期从输入框实时读取,可运行中调整。

### 5.3 超时语义:一次超时就会断开连接

`sendCommand` 超时走 `abortRequests` → `failAll` + `disconnect()`,这是**故意的**
(防止迟到响应错配)。因此:轮询用**更宽松的超时**(1200ms,而往返实际只有几毫秒);
失败**连续 3 次**才停;`disconnect()` 里会调 `i2cStopPoll()` 复位按钮状态。

### 5.4 读-改-写是写入安全的底线

手打 HEX 改位段最大的坑是**覆盖同寄存器其它 bit**。例如 MPU6050 的 `0x1C`:
`AFS_SEL` 在 bit3-4,而 bit0-2 也是有效配置位 —— 直接写 `0x10` 会把低 3 位清零。

所以 `type:'bits'` 的字段一律走:**读当前值 → `(cur & ~mask) | (new << bit)` → 写回**。
日志会打印 `0x00 → 0x10(只改 bit3..bit4)`,写明只动了哪几位。

### 5.5 `calc` 用 `new Function`(等效 eval)的取舍

把 `calc` 变成可粘贴的 JS,必然要动态求值。**这是刻意的选择**:

- **收益**:表达能力不封顶。BMP280 补偿算法、AHT20 的 20-bit 跨字节打包写成正常 JS 就行。
- **风险**:代码来自用户自己的 AI 会话、跑在用户自己的浏览器里,不是网上加载的第三方脚本。
- **限制**:严格 CSP 环境会拦 `new Function`;`file://` 双击打开与 `python -m http.server` 都没有 CSP。

### 5.6 启用时的校验

点「解析并启用」会逐项检查并**指出第几个字段错了**,而不是笼统报"定义无效":

- `key` 是否重复、`label`/`group` 是否齐、`reg` 是否存在;
- `type` 是否在允许列表内(能抓到 `'s16be'` 这种自造写法);
- `type:'bits'` 是否给了 `bit`/`bits`;
- 用了 `calc` 是否配了 `deps`;
- `commands` 是否有 `reg` + 非空 `data`。

### 5.7 本地存储

全部包在 try/catch 里(`file://` 下可能被拒绝,功能降级但页面不报错):

| 键 | 内容 |
| --- | --- |
| `iodock.i2c.defSrc` | 当前编辑框内容(下次打开自动恢复) |
| `iodock.i2c.defs` | 命名保存的定义集合 `{名称: 定义源码}` |

## 6. 性能预期

走文本协议、USB CDC。**注意:左上角波特率选择框对 CDC 无效**,`baudRate` 只是 Web Serial 的占位参数,
调到 921600 不会提速。

单帧开销(14 字节读):TX `I2C READ 0x68 0x3B 14\n` 约 21 字节 +
RX `OK I2C READ HEX:` + 28 hex + `\n` 约 46 字节。

实际瓶颈不是 USB,而是固件主循环往返延迟与 `i2c_read_reg`(`firmware/src/drivers.c`)。
经验值:**默认 20ms 周期(50Hz)是稳妥区间**,与 demo 一致;400kHz 总线读 14 字节本身仅约 0.4ms。
**提升帧率最有效的手段是让 `poll:false` 用到位、把每帧的读取次数压到 1** ——
这正是界面要显示读取计划的原因。

想再快只能引入二进制模式(`BIN ENTER`,OP 0x44)或固件新增流式命令 —— 均不在本次范围。

## 7. 内置定义:只做 MPU6050

内置模板**只有 MPU6050 一份**,因为它是唯一一份**已由可运行代码验证过**的定义 ——
数值直接取自实际跑通的 `demo/demo_mpu6050_iic.html`,不存在「凭印象写寄存器」的风险:

- 初始化:`0x6B=0x00` 唤醒、`0x1A=0x03` DLPF 44Hz、`0x1C=0x00` 加速度 ±2g、`0x1B=0x00` 陀螺 ±250°/s
- 实时数据(7 个):`0x3B..0x48` 大端有符号 `ax ay az temp gx gy gz`,
  加速度 `div:16384`(±2g)、陀螺 `div:131`(±250°/s)、温度 `div:340, bias:36.53`
- 状态(2 个):`WHO_AM_I`(0x75)、睡眠位(0x6B bit6)
- 配置(5 个):加速度量程、陀螺量程、低通滤波、采样分频、时钟源 —— 其中 4 个标了 `write:true`
- 命令(3 个):唤醒、复位所有寄存器(⚠)、复位信号通路(⚠)
- 共 14 个可读量,分成 3 组;默认只勾「实时数据」的 7 个,正好合并成 **1 次** I2C READ

> **`init` 写的量程必须与 `div` 一致**:`init` 把 `0x1C`/`0x1B` 写成 `0x00`(±2g / ±250°/s),
> 所以 `div` 用 16384 / 131。改了 `init` 就必须同步改 `div`,否则数值会差整数倍。

**其它芯片(SSD1306 / BMP280 / AHT20 / ADS1115 / INA219 / DS3231 / PCF8574 / SHT31)不预置。**
理由是这些器件的寄存器表必须逐个对着数据手册核对,而本环境**没有可用的核对渠道**
(设计期间两次尝试联网核对的后台子代理均失败无输出)。发布未核对的寄存器值比不发布更糟。
有了 §4 的定义机制,用户自己让 AI 生成即可,不需要仓库预置。

几个已知的坑(写定义时留意):

- **DS3231 与 MPU6050 同在 0x68**,且 DS3231 **没有 WHO_AM_I**,无法可靠自动识别;
- **SSD1306 / PCF8574 没有任何 ID 寄存器**,同样不能自动识别;
- **BMP280 补偿算法非线性**,要用 `deps` + `calc`;
- **AHT20 是 20-bit 跨字节打包**,且触发测量后必须延时 —— 延时用 `init` 里的 `delay`,
  但「每次读取前都要触发」这种时序**当前不支持**,需要固件侧配合;
- **INA219 要先写分流校准寄存器**才能换算电流 —— 用 `commands` 写校准值即可。

## 8. 接一个新器件

### 8.1 该给 AI 什么

**必须给**(按重要性排序):

| 数据手册章节 | 为什么需要 |
| --- | --- |
| **寄存器映射表**(Register Map / Address Map) | 决定每个字段的 `reg`/`len` —— 最关键 |
| **寄存器描述**(Register Descriptions) | 位段、量程编码、睡眠位、只读位 → 决定 `bit`/`bits`/`enum`/`write` |
| **典型应用 / 初始化流程** | 决定 `init` 写哪些寄存器、什么顺序 |
| **灵敏度 / 量程表**(Sensitivity、LSB per unit) | 决定 `div`/`mul`/`bias` |
| **身份寄存器**(WHO_AM_I / ID) | 用来先验证通信是否正常 |

**可以不给**:封装尺寸、订购信息、绝对最大额定值、焊接曲线 —— 与解码无关。

**手册太大 / 拿不到 PDF 时的三种替代**:

1. 让 AI 自己去查:「先联网找 XXX 的寄存器映射和初始化流程,再按模板输出」。
2. **指向开源驱动**(往往比啃 PDF 更可靠):Adafruit / SparkFun 的 Arduino 库、
   Linux 内核 `drivers/iio/`、Bosch 官方驱动 —— 里面直接就有寄存器地址和换算公式。
3. 只粘**你真正需要的那个功能的章节**。

**务必说清型号变体**:BMP280 与 BME280、MPU6050 与 MPU6500、AHT10 与 AHT20
寄存器并不通用,给错型号会得到一份"看起来很合理但是错的"定义。

### 8.2 提示词

**提示词就在页面里**:点「📋 复制给 AI 的提示词」即可,它会自动把当前编辑框里的定义
作为已验证样例嵌进去。模板本体是 `web/index.html` 里的 `I2C_PROMPT` 常量 ——
**这里不再抄一份,避免两处漂移**(本文档上一版抄的副本已经因为格式升级而失效)。

模板强制约束了这几件事,少一件都会踩坑(模板约 8 KB,是一份完整规格而不是一句话):

- **先说清运行环境与边界**:板子只有两条 I2C 原语、每次只能读一段连续寄存器,
  以及**网页已经代劳了哪些事**(合并读取、换算、反向换算、读-改-写、读回校验、画图、CSV),
  免得 AI 去重复表达或试图发自定义时序;
- **必须是裸 JS 对象字面量**,不要 markdown 围栏、不要 `import`;
- **逐项列出 `fields` 的全部属性**:`key/label/group/desc/unit/reg/len/type/endian/bit/bits/mul/div/bias/enum/plot/poll/write`,
  每项都给了例子和默认值;
- **`poll` / `plot` / `group` 的决策规则独立成节** —— 哪些当初次轮询、哪些设 `poll:false`、
  哪些该画曲线,并给出目标:「让每帧只需 1 次 I2C READ」;
- **写入的两条规则**(位段必须 `type:'bits'`;占满整寄存器才用整数类型);
- `commands` 的写法与 `confirm:true` 的使用场合;
- **`deps` + `calc`** 的写法,以及 `calc` 只能调用哪些注入的助手
  (否则 AI 会自造 `readInt16BE` 之类的函数名);
- **三个典型形态示例**(单值传感器 / 多轴 IMU / 需校准补偿),说明不同复杂度的写法;
- **13 条提交前自查清单**(字节序、睡眠位、延时、只读位、量程与 div 一致性、分组与 poll 等);
- 要求额外回报:身份寄存器地址与期望值、地址冲突、如何确认在出数据、
  **预估每帧读取次数与帧率**、以及「没把握的地方标出来,不要编」。

### 8.3 拿到定义后怎么验

1. **先验通信,再验数据**:用手动读写卡单独读身份寄存器(如 `0x75`),确认能读回期望值。
   这一步失败就与 `decode` 无关,是接线 / 地址 / 上拉 / 速率的问题。
2. 粘进编辑框 → 点「✓ 解析并启用」。校验失败会指出**第几个字段**错了。
3. 点「⚡ 初始化设备」→ 日志逐步显示每次写;任一步失败会明确说是第几步。
4. 点「读一次」看数值是否合理;顺便看计划提示里的读取次数是否符合预期。
   想看配置/状态就点「📖 读全部量」。
5. **数值离谱时的排查顺序**:

   | 现象 | 原因 |
   | --- | --- |
   | 差 256 倍左右 | 字节序反了,该字段加 `endian:'le'` |
   | 差整数倍(2×、4×) | `div` 与 `init` 设的量程不一致,或 `init` 没执行 |
   | 一直是常数不动 | 器件还在睡眠 / 待机态,`init` 缺唤醒那一步 |
   | 全是 0 或全是 FF | 大概率没读到(地址错 / NACK),看日志 |
   | 数量级对但抖动巨大 | 可能读到未就绪的数据,需查数据就绪位或提高周期 |
   | 位值总是 0 | `bit`/`bits` 写错了,用寄存器浏览器对一下原始字节 |

6. **验写入**:先读回当前值,再写一个新值,看日志里「只改 bitX..bitY」的说明和读回值。
   写完再用寄存器浏览器读整个寄存器,确认其它 bit 没被破坏。
7. 合理了就点「保存」起个名字,下次从下拉框载入。

## 9. 明确不做

- **不做任意 I2C 事务组合器**(多段自定义时序)—— 固件不支持,网页无法凭空造出。
- **不给每颗芯片加独立标签页** —— 那等于把「写独立网页」的问题搬进 index.html。
- **不预置未核对的寄存器表** —— 见 §7。
- **不做「让用户逐个勾选要读的量」的界面** —— 试过,已去掉:那等于把配置负担推给用户,
  与「AI 辅助下快速读取展示」的目标相反。读什么由定义里的 `poll`/`plot` 表达。
- **不支持「每次读取前必须先触发一次测量」的器件**(如 AHT20 的测量触发时序)——
  当前轮询只有「读」没有「写前置」,要支持需固件侧配合或扩展定义格式。
- **不改固件**。若将来要跑 >200Hz 或需板卡脱机连续采集,再讨论新增 `I2C SAMPLE`
  流式命令(参照 `ADC SAMPLE` 的 DATA 流实现)。

## 10. 已验证

**离线验证全部通过**(直接抽取 `web/index.html` 里的**真实代码**测试,不是重新实现):

**合并读取(12 项)**

- 7 个连续寄存器 → 1 次读取,区间正确为 `0x3B+14`
- 加远处寄存器 → 2 次;再加一个 → 3 次;输出按地址升序
- 同一寄存器两个位域 → 1 次;恰好相接 → 合并;间隔 1 字节 → 不合并
- 乱序输入也能正确合并
- 250 字节超 200 上限 → 自动拆成 200 + 50

**解码(15 项)**

- `s16` 大端带 `div`、`u8`、`bits`(不同起始位/位宽)、`enum` 命中与**未命中回退数字**
- `bias` 偏移、`ascii`、`float32`、`deps`+`calc`
- `len` 由 `type` 推导(s16=2 / float32=4 / bits=1)

**写入(13 项)**

- 物理值 → 原始值 → 字节的反向换算;`s16` 大端/小端;负数
- 超范围夹紧(u8 999→255、u8 -5→0、s16 99999→32767)
- **往返一致**:`1g → 字节 → 解码回 1g`
- `bits` 不走 `encode`(由 RMW 处理)、`float32` 明确报错不静默失败

**内置 MPU6050 定义自检(24 项)**

- 14 个字段 / 3 条命令;`key` 无重复;每个字段都有 `group` 和 `label`
- 类型全合法;`bits` 字段都给了 `bit`/`bits`;没有 `calc` 字段被标可写
- 命令都有 `reg`+`data`;危险命令都带 `confirm`
- **`init` 与 `div` 一致性**:`0x1C`/`0x1B` 写 `0x00` ↔ `div` 为 16384 / 131
- **轮询 7 项 / 按需 7 项**;轮询的 7 项正好合并成 **1 次**读取(区间 `0x3B+14`)
- 全部 14 个量合并成 4 次读取(区间 `0x19+4 0x3B+14 0x6B+1 0x75+1`)—— 「读全部量」的实际开销
- 状态组与配置组全部 `poll:false`;`plot` 的 7 项正好就是轮询的那 7 项
- 可写字段全部带 `poll:false`(改配置不会拖慢轮询)
- 走真实的 `i2cPollFields()` / `i2cOneshotFields()` 函数验证数量,不是只看对象属性

**页面结构(16 项)**

- 整段脚本解析通过;62 个脚本引用 id 全部存在;57 个 `onclick` 函数全部有定义
- 9 个标签页与面板配对;`div` 166/166、`section` 9/9 标签平衡

- 提示词确认含 20 个关键段落(任务/边界/代劳清单/属性全表/poll 决策/写入规则/
